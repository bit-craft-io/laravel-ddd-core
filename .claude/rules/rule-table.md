# テーブル設計

このファイルは、テーブルの設計の思想と、規則を定める。クラスの責任は、`rule-coding.md` を参照する。

- `※要判断` は、未確定。確定したら、印を外す。

## 種別と名前

- テーブルは、役割で 3 種類に分ける。`m_`(マスタ)、`u_`(ユーザ)、`t_`(履歴・取引)。
- 名前は、`{種別}_{名前}` の、複数形のスネークケース。
- モデル、Ds、VoM は、テーブルに対応させる。テーブル `m_{名前}` は、モデル `M{名前}`、Ds `DsM{名前}`、VoM `VoM{名前}`(`{名前}` は単体形のパスカルケース)。`u_` と `t_` も、同じ形。R1〜R3 は、`CLAUDE.md` を参照する。
- core が持つテーブルは、下の「例外」を参照する。

## 外部キー

- 子の表から、親の表への参照の列(`user_id`、`{名前}_id`)には、外部キー制約を張る。
- `u_` の `user_id` は、`u_users.id` を参照する。
- 削除時の動作は、`restrict` を既定にする。物理削除をしないため、外部キーの役目は、親の無い行を作らせないこと。
- 連動削除(`cascade`)は、親と子が一体のときだけ(例: `u_users` は、`accounts` に連動する。下の「例外」)。※要判断
- マイグレーションは、親の表を先に作り、子の表を後に作る(削除は、逆の順)。core のテーブルは、core のマイグレーション(R8)を、先に実行する。※要判断
- ソフトデリートは、外部キーが見ない。親を論理削除しても、子は残る。論理削除の整合性は、実装が見る。

## 削除とマスク

- テーブルは、基本的に、物理削除しない。`u_` は論理削除(`deleted_at`)、`m_` は `is_active` と期間で、公開を管理する。
- 個人を特定する情報は、マスクする。マスクした行は、検索から除外する。
- マスクした行は、`deleted_at` を立てて、ソフトデリートの絞り込みで外す(`deleted_at` が、マスク済みの印を兼ねる)。※要判断
- ユニークキーのある列は、マスクした値も一意にする(例: id を含める)。※要判断
- マスク対象の列は、列のコメントなどで示す。※要判断
- 退会時は、Sanctum のトークンを失効させる。※要判断

## マスタ(`m_`)

- 運営が管理する参照データ。アプリは、更新しない。
- 公開の判定は、`is_active`(公開中)と、有効期間(`begin_at` / `end_at`。null は無期限)で行う。`BaseMstDs` の `getEnable()` と `findEnable()` が、この列で絞る。
- `deleted_at` は、持たない。公開の管理と、紛らわしくなるため。
- 共通の列: `id`、`is_active`、`begin_at`、`end_at`、`name`、`display_order`(必要なら)、`ops_memo`(運用メモ)、`created_at`、`updated_at`。
- 対応表のように、公開の概念がないものは、`is_active` と期間を持たなくてよい。※要判断

## ユーザ(`u_`)

- ユーザごとの状態。内部用ユーザ識別子 `user_id` を持つ。
- 時刻の列は、`created_at`、`updated_at`、`deleted_at`(ソフトデリート)。
- 「1 ユーザ × 1 対象 = 1 行」のものは、`user_id` と対象の識別子の複合ユニークキーで保証する。
- 論理削除した行も、ユニークキーを占有する。同じキーで再作成するときは、復元(restore)する。※要判断
- 構造が可変な状態は、JSON 列に寄せ、Vp が包む。※要判断
- 履歴が、ユーザの記録と一体で、状態の更新がないときは、`u_` が履歴を兼ねてよい(別に `t_` を作らない)。※要判断

## 履歴・取引(`t_`)

- 時刻の列は、`created_at`、`updated_at`。`updated_at` があるのは、状態が更新されるため(例: 決済は、作成時に「購入中」、完了時に「購入完了」へ更新する)。
- 状態は、進捗の種別の列で表す(例: `type_progress`)。
- 取引の重複を防ぐ識別子には、ユニークキーを付ける。
- `deleted_at` は、持たない。※要判断

## 列の共通の規則

- 主キーは、`id`(コメント「識別子」)。
- すべての列に、日本語の `comment()` を付ける。
- 種別は、`unsignedTinyInteger` の `type_{名前}`。列のコメントに、値を列挙する(例: `（1: 種別A | 2: 種別B）`)。モデルで、PHP の enum に cast する。
- 真偽値は、`boolean` で、名前は `is_*`。
- 日時は、モデルで `datetime:Y-m-d H:i:s` に cast する。
- ユーザ識別子は、内部用の `user_id` を使う。外部公開用の識別子(`public_id`)は、「例外」の `u_users` が持つ。

## 例外(core が持つテーブル)

core が持つ次のテーブルは、この規則の例外として、名前を固定で書く。

- `accounts`: 認証。種別の接頭辞を持たない。`email` にユニークキー。列のコメントを持たない(Laravel の標準に近い形)。`deleted_at` を持たない。
- `u_users`: プロフィール。主キー `id` が、`accounts.id` への外部キー(削除時は、連動して削除)。外部公開用の識別子 `public_id` を持つ(ユニークキー)。`deleted_at` を持たない。
- Laravel と Sanctum の標準のテーブル(`password_reset_tokens`、`sessions`、`personal_access_tokens` など)は、この規則の対象外。※要判断

## 未決事項

- 既存の `u_items`、`u_gachas`、`u_idles` に、外部キーと `deleted_at` を足すか(新しいテーブルからだけ、とするか)。
- `accounts` と `u_users` に `deleted_at` を足すか(マスクと検索除外の仕組みに必要なら)。
- マスタを入れ替える運用(インポート)の作法(物理削除をしない、の具体)。
- 個人を特定する情報の範囲(`u_users.meta_data` の扱いを含む)。
